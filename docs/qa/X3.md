## Primary check (from the run doc's Named edge-case register)
"Assign a member, reschedule before the welcome sends — welcome carries the new time, exactly one welcome" (idempotency under racing events).

**This edge case is structurally unreachable as worded, and that's worth understanding, not just asserting.** The run doc's own investigation (see PR description) found there's no Inngest pipeline or send queue anywhere in this codebase — every notification, including the new welcome message, sends synchronously inside the same admin action that triggers it. There is no window between "assigned" and "welcome sends" for a reschedule to race into - the welcome reads the session's current `scheduled_at` at the exact moment it fires and is gone before the admin action even returns. A reschedule that happens genuinely afterward is a separate real event, correctly handled by P4's own pre-existing `session_rescheduled` notification, not by X3's welcome. Verify this reasoning by reading `lib/admin/assignment.ts`'s `assignApplicantToCohortAction` end to end - the RPC call, the notification call, and the redirect are the entire function body, nothing async in between.

1. Complete a real intake (use `/refer/riverside-health`, same flow L2's own QA doc uses) through to confirmation.
   **Expect:** in Supabase Studio, a new `notification_log` row for that applicant with `notification_type = 'application_received'`, `status = 'sent'` (or `'failed'` if Resend isn't configured locally - check `send-email.ts`'s own log output either way). Open Mailpit and read the email: should say "We have your information. We'll be in touch within three business days." - nothing about dementia, caregiving, or the group.
2. In `/admin/applicants`, assign a pending_review applicant (with a `pending_review` cohort that has a real session 1) to that cohort.
   **Expect:** a `notification_log` row with `notification_type = 'cohort_assigned'`. Read the email in Mailpit: first session date/time (should say "your time" only if the applicant's own time zone differs from the cohort's), a join link, dial-in number if the session has one, and the same "what to expect" sentence already shown on `/status/[applicantId]` for L4's assigned state. No facilitator name anywhere - that's correct, not a bug (no name column exists in the schema yet).
3. In `/admin/cohorts/[id]`, mark an active cohort completed (needs at least one real enrolled/attending applicant on it).
   **Expect:** in Supabase Studio, that applicant's own `applicants.status` is now `'completed'`, not `'enrolled'` - a real gap X3 fixed, not pre-existing behavior. A `notification_log` row with `notification_type = 'program_complete'`. The email should read: "You've completed {the real program name}. There's no other program open for you right now. If that changes, we'll reach out." - the exact same sentence L4's own completed-status screen shows.
4. Read all three message bodies from steps 1-3 aloud.
   **Expect:** plain, warm, no mention of dementia, caregiving, medications, or the group's composition anywhere - matches the existing voice of the reschedule/cancel messages already in production.

## Known gap: message 3 (Waitlisted) is not built
No code path anywhere transitions an applicant into a distinct "waitlisted" state - the same `hasMatchingCohort` gap L4/L5 already documented (no real "does a matching cohort exist" signal exists without inventing an auto-matcher, which the no-auto-matcher invariant forbids). Not attempted here.

## Known gap: message 7 (sign-in) still uses a separate delivery path
Sign-in magic-links/OTP codes are sent entirely by Supabase Auth's own built-in SMTP/SMS config (`lib/auth/actions.ts`'s `signInWithOtp` calls) - there's no code path connecting them to `notification_log`/the staging-guard/`lib/messaging/` at all. Unifying them is real, separate work, left as an explicit follow-up decision rather than silently built or silently skipped.
